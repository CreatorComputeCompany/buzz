# Buzz Orca host

This directory is the source of truth for the two systemd services on
`buzz-orca-host.boxd`:

- `orca-serve.service` runs the headless Orca runtime and embedded web client.
- `buzz-orca-agent.service` listens to Buzz and dispatches work to that runtime.

The agent is both `Requires=` and `PartOf=` the runtime. `Requires=` prevents an
agent without a runtime; `PartOf=` makes `systemctl restart orca-serve` restart
the agent in the same transaction. This matters because a dependency stop is a
clean exit, and no `Restart=` policy treats a systemd-requested clean stop as a
failure.

## Secret files

The checked-in units contain no credentials. Before installing them, create
these root-owned mode-0600 files on the host:

- `/etc/orca-serve.env` — `ORCA_RUNTIME_APP_TICKET_SECRET`, also configured on
  the Buzz web API.
- `/etc/buzz-orca-agent.env` — the managed Buzz agent key, auth tag, owner, and
  response allowlist generated by `desktop/scripts/provision-hosted-orca-agent.mjs`.

Do not print either file in logs or copy it back into the repository.

## Install or update services

Copy this directory to the host, review the diff against `systemctl cat`, then:

```bash
sudo ./install-services.sh
systemctl status orca-serve.service buzz-orca-agent.service
```

The installer validates the secret-file ownership before replacing either
unit. It removes the old identity, logging, and lifecycle drop-ins because
those settings are represented in the complete units.

## Deploy an Orca application bundle

Build Orca's `out/main` and `out/web` directories from one reviewed commit and
publish them as separate GitHub release archives whose roots are `main/` and
`web/`. On the host, download those immutable assets and retain their GitHub
SHA-256 digests. Then run:

```bash
sudo ./install-bundle.sh \
  /tmp/orca-main.tgz MAIN_SHA256 \
  /tmp/orca-web.tgz WEB_SHA256
```

The installer verifies both digests and archive layouts before stopping
anything. It swaps both directories while the services are offline, starts the
runtime and listener together, waits for the public runtime health check, and
automatically restores the previous directories if startup fails. Successful
deploys retain timestamped `main.before-*` and `web.before-*` rollback copies
under the Orca `out` directory; pruning those is a separate reviewed operation.

## Verify restart coupling

This deliberately restarts the production runtime, so use it during a planned
verification window:

```bash
before_runtime=$(systemctl show -p MainPID --value orca-serve.service)
before_agent=$(systemctl show -p MainPID --value buzz-orca-agent.service)
sudo systemctl restart orca-serve.service
systemctl is-active --quiet orca-serve.service
systemctl is-active --quiet buzz-orca-agent.service
test "$(systemctl show -p MainPID --value orca-serve.service)" != "$before_runtime"
test "$(systemctl show -p MainPID --value buzz-orca-agent.service)" != "$before_agent"
```

The public runtime can return 502 while Electron boots. Wait for its HTTP
endpoint to recover before running a chat acceptance test:

```bash
until curl -fsS https://runtime.buzz-orca-host.boxd.sh/ >/dev/null; do sleep 2; done
```

## Rollback

Keep a copy of the previously installed unit files before an update. Restore
both files, run `systemctl daemon-reload`, and restart both units. Service
rollback does not roll back the Orca application bundle or its data profile.
